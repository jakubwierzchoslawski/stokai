## 1. System Overview

StokAI is a geopolitical intelligence platform for retail investors. Its core value proposition is compressing 20–40 minutes of manual analyst synthesis into 90 seconds: when a geopolitical event occurs, the system automatically identifies which portfolio companies are affected, retrieves historical analogies, and produces a confidence-scored action recommendation — all before the average retail investor hears about it.

The world map is the primary decision interface, not a visualization layer. Events pulse on the map; each pulse is connected to affected companies, their custom scores, and the AI analysis that explains why the event matters for the investor's specific holdings.

The system operates in two fundamentally different execution modes that share a single database, memory subsystem, tool library, and observability stack:

- **Mode A (Reactive Pipeline):** A deterministic, fixed 12-step sequence that converts real-time events (tweets, GDELT polls, SEC filings, price anomalies) into user alerts within 90 seconds at approximately $0.05 per event. No agents, no loops, no branching — predictability is the requirement.

- **Mode B (Deliberative Workflows):** A LangGraph-orchestrated agentic system where nine named-role agents produce deep analytical reports via five scheduled or on-demand workflows. Target latency: 2–5 minutes. Target cost: $0.50–$2.00 per report.

The two modes are not separate systems — they are two operating modes of one system, optimized for different latency profiles. Mode A is the publisher: every significant event triggers both an immediate alert (Mode A) and an asynchronous deep-dive (Mode B).

## 2. Architecture Principles

Five immutable principles govern every implementation decision. Violating any one of them creates technical debt that blocks scaling.

### Principle 1 — Everything Behind an Interface

No business layer touches a data provider, a specific market, or a specific database directly. Every external dependency sits behind a protocol interface. Changing the price provider from Finnhub to any alternative means a new interface implementation with zero changes to scoring, map, or alert logic.

Applies to: `PriceProvider`, `FundamentalsProvider`, `NewsProvider`, `SocialProvider`, `FilingsProvider`, `MacroProvider` — and to the repository pattern for all DB access.

### Principle 2 — Local-First Data

Every external API response is saved locally with a timestamp and TTL. Before every external call, the system checks: (1) Redis hot cache, (2) local PostgreSQL. Only on a cache miss is the API called. Historical data and event embeddings have infinite TTL — fetched once in the system's lifetime.

Effect: the monthly API bill is flat and predictable regardless of how many times the same data is queried in the UI.

### Principle 3 — Multi-Tenant Schema, Single-Tenant Operations

Every user data table carries a `tenant_id` column from day one. Operationally, one tenant exists. Adding more tenants later requires configuration, not schema migration.

### Principle 4 — Containerized and Portable

The entire system runs in Docker containers. No dependency on Azure-only services where a portable alternative exists. Self-hosting is a change of environment variables and `docker compose up` — not a rewrite. Complies with 12-factor app conventions.

### Principle 5 — Transparent AI

Every AI recommendation carries a confidence score, historical sample size, and a traceable reasoning chain. The system never pretends to certainty it does not have. Recommendations are decision frameworks, not transaction signals. Every reasoning step is stored in the database for audit and override.

## 4. Six-Layer System Model

The system is organized into six layers. The boundaries are strict: the presentation layer never calls provider APIs, and the processing layer never bypasses the storage abstraction.

```
Layer 1 — External World (signal sources)
  ├── Market prices        Finnhub.io (REST + WebSocket)
  ├── Fundamentals         Financial Modeling Prep
  ├── Geopolitical events  GDELT (15-min poll, 1979+ historical archive)
  ├── Macro indicators     FRED
  ├── Filings              SEC EDGAR (real-time feed)
  └── Social signals       Twitter/X Filtered Stream (off by default, D8)
  Each source is behind a protocol interface — replaceable without
  changing any business logic above this layer.

                           ↓

Layer 2 — Ingestion & Cache (local-first)
  ├── Provider Adapters    Implementations of PriceProvider, NewsProvider, etc.
  ├── Cache-or-Fetch       Redis → PostgreSQL → API (only on miss)
  ├── Ingestion Scheduler  Celery beat — poll jobs, TTL enforcement
  ├── Data Validator       Schema validation at the boundary
  └── Rate Limiter         Per-source counters in Redis

                           ↓

Layer 3 — Storage (local, persistent)
  ├── PostgreSQL 16        Relational entities, agentic memory tables
  ├── TimescaleDB          OHLCV price hypertables, company_score snapshots
  ├── pgvector             Event embeddings, semantic_fact embeddings (HNSW)
  └── Redis 7              Hot cache + Celery task queue broker

                           ↓

Layer 4 — Processing (AI & Analytics)
  ├── Mode A               Reactive Pipeline (12-step deterministic)
  ├── Mode B               Deliberative Workflows (LangGraph StateGraph)
  ├── Scoring Engine       DSL parser, normalization, geo-modifier
  ├── Exposure Mapper      Event → Company via geo_revenue + sector
  └── Memory Subsystem     Four-layer agentic memory

                           ↓

Layer 5 — Serving (API)
  ├── REST API             FastAPI, /api/v1, JSON envelopes
  ├── WebSocket            Real-time event delivery to frontend
  └── Alert Dispatcher     Email (SendGrid), push (future)

                           ↓

Layer 6 — Presentation (frontend)
  ├── Intelligence Map     MapLibre GL JS, WebGL pulses, Supercluster
  ├── Side Panel           Progressive disclosure: popup → panel → deep dive
  ├── Screener             Sortable company table, geo-overlay filter
  ├── Reports Reader       Morning Brief, Deep-Dive memos, HIL feedback
  ├── Q&A Chat             Interactive Historical Context Q&A
  └── Admin Panel          /admin route, role-gated, all config plane controls
```

## 5. Backend Module Map

The backend is a modular monolith. Modules communicate through injected interfaces, never through direct imports of concrete classes from other modules. Extraction into separate services is possible without rewriting business logic.

| `markets` | Market abstraction. Per-market configuration (calendar, timezone, currency, ticker format, sector taxonomy) loaded from `source_config` + `market_source_binding` tables (D1). | `storage` |
| `scoring` | DSL parser, AST evaluator, normalization (percentile/z-score/min-max), geo-modifier, benchmark engine. | `storage` |

| `ai` | Agent Registry, Tool Library, LangGraph workflow graphs, Memory Subsystem, Langfuse integration, prompt loading, confidence computation. | `storage` |
| `historical` | Pattern matching, pgvector semantic search, analogy statistics, time-machine data isolation (no future data leakage). | `ai`, `storage` |

## 6. Mode A — Reactive Pipeline

Mode A is the deterministic, non-agentic real-time path. It has no tool loops, no decision branches, and no agents. Each LLM call has a fixed, narrow purpose with bounded token budgets.

**Triggers:** X (Twitter) Filtered Stream · GDELT 15-min poll · SEC EDGAR filing · Price anomaly detected by ingestion.

**End-to-end SLA:** ≤ 90 seconds from event arrival to user alert.

**Step sequence (D5 — 12 steps, authoritative):**

| Step | Type | Operation | Model / Target | Latency |
|------|------|-----------|----------------|---------|
| 1 | Deterministic | `persist_raw_event` — write raw payload to `geo_event.raw` before any processing | — | < 1s |
| 2 | LLM | `classify_event` — category[], intensity (1–5), sentiment, regions[], affected_sectors[], cameo_code | Haiku 4.5 · 2k in / 200 out | < 5s |
| 3 | LLM | `extract_tickers` — companies directly mentioned or implied by the event | Haiku 4.5 · 1k in / 100 out | < 3s |
| 4 | Deterministic | `compute_exposure_map` — DB lookup of `geo_revenue` + sector matching to find all affected companies | — | < 3s |
| 5 | Deterministic | `persist_event_record` — write final `geo_event` row + `event_exposure` rows | — | < 1s |
| 6 | LLM | `embed_event` — vectorize event text, persist `VECTOR(1536)` to `event_embedding` pgvector table | OpenAI text-embedding-3-small · 500 in | < 2s |
| 7 | Deterministic | `find_historical_analogies` — pgvector HNSW top-K cosine search over `event_embedding` | — | < 3s |
| 8 | LLM | `generate_alert_text` — ~80-word alert summary incorporating top analogies | Sonnet 4.6 · 3k in / 200 out | < 8s |
| 9 | Deterministic | `evaluate_alert_rules` — check `alert_rule` rows for the tenant; apply intensity filters, scope filters, deduplication, anti-fatigue counters | — | < 1s |
| 10 | Deterministic | `dispatch_or_log_silent` — if rules match: send email/push via SendGrid; else: write silent-log entry | — | < 2s |
| 11 | Deterministic | `enqueue_deep_dive` — if event.intensity ≥ 4 or portfolio match: enqueue Event Deep-Dive workflow (Mode B) with 2-minute delay to allow market to react | — | < 1s |
| 12 | Deterministic | `return_pipeline_result` — write episodic memory entry; return structured result to caller | — | < 1s |

**Total LLM time budget:** ~18 seconds across all four LLM calls.
**Total pipeline budget:** ≤ 60 seconds of processing; 30-second margin to 90s SLA.

**Mode A output artifacts:** An `alert` row (if rules matched), a persisted `geo_event`, an `event_embedding` in pgvector, an episodic memory entry, and optionally an enqueued Mode B job.

**Observability:** Every event produces one Langfuse trace. Every LLM call is a logged span with prompt version, model, token counts, latency, and cost. Tier 3 ex-post calibration applies (did the classifier get the category right?).

**Mode A → Mode B handoff:**
```python
# Step 11 enqueue logic
if event.intensity >= 4 or event.matched_portfolio_company:
    workflow_queue.enqueue(
        workflow_type="event_deep_dive",
        inputs={"event_id": event.event_id},
        priority="high",
        scheduled_for=now() + timedelta(minutes=2),
    )
```
The user receives the 80-word push alert within 90 seconds and the deep-dive memo within ~10 minutes.

## 7. Mode B — Deliberative Workflows

Mode B is the agentic system where analytical judgment determines flow. It uses LangGraph StateGraph with two node types and nine named-role agents.

### 7.1 LangGraph Runtime

**Framework:** LangGraph (Python). Celery workers host the workflow runtime. Long-running workflows (the Morning Brief can take 4–5 minutes) run as Celery tasks.

**Two node types — the binary distinction:**

```
DeterministicNode  — plain Python function: (state) → state
                     No LLM, no agent. Fetch, transform, format, dispatch.
                     Use when: the work is mechanical and fully determined by inputs.

AgentNode          — named-role agent with persona, system prompt, scoped tools, model config.
                     Use when: analytical judgment is required.
                     Decision rule: "Would a human analyst need to think about this?"
```

**State object (Pydantic, passed between all nodes):**

```python
class WorkflowState(BaseModel):
    workflow_id: UUID
    workflow_type: WorkflowType
    tenant_id: UUID
    user_id: UUID
    started_at: datetime
    inputs: dict[str, Any]
    portfolio_state: PortfolioState | None = None
    events: list[GeoEvent] = []
    relevant_events: list[RelevantEvent] = []
    score_changes: list[ScoreChange] = []
    anomalies: list[Anomaly] = []
    analogies: dict[UUID, list[Analogy]] = {}
    recommendations: list[Recommendation] = []
    report: Report | None = None
    confidence_scores: dict[str, float] = {}
    requires_hil: bool = False
    hil_reason: str | None = None
    cost_usd: float = 0.0
    tokens_consumed: dict[str, int] = {}
```

**Checkpointing:** PostgreSQL-backed LangGraph checkpointing is mandatory for three reasons: (1) failure recovery — resume from the last successful node without redoing prior work; (2) HIL pause/resume — the graph is paused, not killed, when routed to the review queue; (3) replay for debugging — any historical run can be re-executed from a checkpoint with a new prompt version.

**Parallelism:** Independent sub-tasks within a node (e.g., Historical Context queries for multiple events) use `asyncio.gather`. Each parallel invocation is a sibling span in the Langfuse trace.

**Bounded execution — enforced per agent YAML:**
```yaml
limits:
  max_input_tokens: 8000
  max_output_tokens: 2000
  max_iterations: 3
  timeout_seconds: 60
  cost_ceiling_usd: 0.30
```
Exceeding any bound fails the agent invocation. The workflow routes to HIL with a "budget exceeded" reason.

**Cross-workflow invariants:**
- `evaluate_quality` is always the second-to-last node in every workflow (computes overall confidence, sets `requires_hil`).
- `Narrative Writer` is always the last AgentNode in every workflow (prose conversion, consistent voice).

### 7.2 Agent Registry (Nine Named Roles)

Each agent is defined in `agents/{role_id}.yaml`. Configuration is data; no code change is required to reconfigure an agent's model, tools, or limits.

| Role ID | Model | Purpose | Scope |
|---------|-------|---------|-------|
| `relevance_analyst` | Sonnet 4.6 | Filter overnight events for portfolio relevance; distinguish signal from noise | Morning Brief, Watchlist Scan |
| `anomaly_detector` | Sonnet 4.6 | Identify statistically unusual score and metric movements | Morning Brief, On-Demand, Watchlist |
| `exposure_analyst` | Sonnet 4.6 | Determine type and magnitude of company exposure to a specific event (direct / supply chain / sector / currency) | On-Demand, Event Deep-Dive |
| `historical_context_agent` | Opus 4.7 | Find historical analogies via pgvector; analyze how affected companies reacted; the most-reused agent | All five workflows |
| `recommendation_synthesizer` | Opus 4.7 | Capstone agent: synthesize relevance, anomalies, and historical context into HOLD/WATCH/BUY_OPP/REDUCE_RISK/HEDGE/CONTRARIAN with confidence | All five workflows |
| `narrative_writer` | Opus 4.7 | Convert structured outputs into readable prose (FT columnist voice, not AI assistant voice) | All five workflows (always last AgentNode) |
| `earnings_context_agent` | Opus 4.7 | Synthesize macro/geo/sector context ahead of an earnings release; produces scenario tree | Earnings Risk Brief |
| `event_deep_dive_agent` | Opus 4.7 | Thorough analysis of a single high-impact event: causes, second-order effects, action implications | Event Deep-Dive |
| `qa_analyst` | Opus 4.7 | Interactive Q&A; broadest tool scope; `max_iterations=10` (only looping agent) | On-Demand Q&A |

**Agent confidence output schema (representative):**
```python
class RelevanceAnalysis(BaseModel):
    relevant_events: list[RelevantEvent]
    excluded_events: list[ExcludedEvent]
    overall_market_tone: str  # "risk_off" | "risk_on" | "mixed" | "quiet"
    confidence: float         # [0, 1]
    reasoning_summary: str
```

**Workflow-level confidence** = minimum confidence across all critical AgentNodes in the workflow. If the Historical Context Agent reports 0.4 confidence (small sample), the workflow's overall confidence is 0.4 regardless of other agents' scores.

### 7.3 Tool Library

Agents never access the database or external APIs directly. They call typed business functions from the Tool Library. This constraint provides safety (no cross-tenant access, no unbounded queries), consistency (standard output shapes), and observability (every tool call is logged).

**Tool design principles:**
- All inputs and outputs are Pydantic models.
- Every tool returns at most 50 rows (bounded output — no accidental context blowup).
- Standard error contract: `ToolNotApplicable` | `InsufficientData` | `RateLimited`.
- Tool results are cached for the duration of a single workflow run.
- Idempotent and side-effect-free. Writing tools are explicitly named (`save_recommendation`, not `process`).

**Tool families:**

| Family | Example tools | Primary agents |
|--------|--------------|----------------|
| Portfolio & User Context | `get_portfolio_state`, `get_watchlist`, `get_user_preferences` | Relevance, Synthesizer |
| Company Data | `get_company_fundamentals`, `get_company_score_history`, `get_geo_revenue_breakdown`, `get_supply_chain_dependencies` | Exposure, Anomaly Detector |
| Events & History | `query_recent_events`, `find_similar_events` (pgvector), `get_price_reaction_to_event`, `compute_event_outcome_statistics` | Historical Context |
| Exposure & Correlation | `get_company_exposures`, `compute_exposure`, `get_sector_correlations` | Exposure, Synthesizer |
| Macro & Market | `get_macro_indicators`, `get_market_baseline`, `compute_zscore` | Anomaly Detector, Earnings Context |
| Memory & Track Record | `query_past_recommendations`, `compute_track_record`, `query_semantic_memory`, `query_user_feedback` | Synthesizer, Q&A |

### 7.4 Four-Layer Memory Subsystem

All four layers are implemented from day one. Together they constitute the learning loop.

| Layer | Storage | What it stores | Update pattern | Retention |
|-------|---------|---------------|---------------|-----------|
| 1 — Episodic | PostgreSQL (`workflow_run`, `agent_invocation`, `tool_call`, `recommendation_outcome`) | Complete record of every run, every decision, every outcome | Append-only | Indefinite |
| 2 — Semantic | PostgreSQL (`semantic_fact`) + pgvector embeddings | Curated entity facts; requires evidence_count ≥ 3 to commit; 6-month confidence decay | Weekly offline extraction job; human approval required | Managed by decay + retraction |
| 3 — Procedural | PostgreSQL (`procedural_pattern`) | Reasoning patterns that correlate with good outcomes | v1: hand-seeded; v2: weekly mining job with human approval | Managed by success rate + retraction |
| 4 — User Feedback | PostgreSQL (`user_feedback`) | Explicit user signals: approve / reject / edit / thumbs / engagement | Direct logging on every HIL action and in-UI feedback | Indefinite |

**Memory hygiene guardrails:**
- Semantic facts require ≥ 3 supporting observations before entering memory.
- Facts and patterns unconfirmed for 6 months have confidence reduced by decay function.
- Users can explicitly retract any fact, pattern, or feedback record via the Admin AI Audit Console.
- A quarterly scheduled task surfaces low-confidence semantic facts for manual review.

**Weekly offline improvement loop:** A scheduled job mines episodic + semantic memory for patterns. It generates proposed prompt adjustments and confidence threshold changes. These proposals surface in the Admin AI Audit Console. No change is applied without human approval. Once approved, changes flow through the standard prompt versioning pipeline.

### 7.5 Five Core Workflows

All five workflows follow the DeterministicNode/AgentNode pattern and share the Tool Library, Memory Subsystem, and observability stack.

**Workflow 1 — Morning Brief**
- Trigger: Daily cron (runs at ~05:30 to target send at 06:00, per D7)
- Budget: ≤ 5 min / ≤ $2.00
- Graph: `fetch_portfolio` → `fetch_overnight_events` → `Relevance Analyst` → `recompute_scores` → `Anomaly Detector` → `Historical Context Agent` (parallel per event) → `Recommendation Synthesizer` → `Narrative Writer` → `evaluate_quality` → [HIL if confidence < 0.7] or [format_email → dispatch]
- HIL fallback: if unreviewed by 05:45, hold and notify user

**Workflow 2 — On-Demand Company Analysis**
- Trigger: User action ("Deep analyze" from Company Detail screen)
- Budget: ≤ 4 min / ≤ $1.50
- Graph: `fetch_company_state` → `fetch_active_events` → `Exposure Analyst` → `Historical Context Agent` → `Anomaly Detector` → `Recommendation Synthesizer` → `Narrative Writer` → `evaluate_quality` → branch
- HIL fallback: if unreviewed in 10 min, deliver with low-confidence banner

**Workflow 3 — Watchlist Scan**
- Trigger: Daily cron at 17:30 (target send 18:00)
- Budget: ≤ 3 min / ≤ $1.00
- Graph: `fetch_watchlist` → `fetch_today_events` → `Relevance Analyst` → `recompute_scores` → `Anomaly Detector` → `Historical Context Agent` (high-anomaly names only) → `Recommendation Synthesizer` → `Narrative Writer` → `evaluate_quality` → branch

**Workflow 4 — Earnings Risk Brief**
- Trigger: Daily cron at 17:30 for portfolio companies with earnings T+1
- Budget: ≤ 4 min / ≤ $1.50
- Graph: `fetch_company_state` → `fetch_earnings_history` → `fetch_macro_context` → `fetch_sector_recent_earnings` → `Earnings Context Agent` → `Historical Context Agent` → `Recommendation Synthesizer` (scenario tree output) → `Narrative Writer` → `evaluate_quality` → branch

**Workflow 5 — Event Deep-Dive**
- Trigger: Enqueued by Mode A step 11 (intensity ≥ 4 or portfolio match), delayed 2 minutes
- Budget: ≤ 7 min / ≤ $2.00
- Graph: `fetch_event_full` → `fetch_market_reaction_so_far` → `Exposure Analyst` (parallel per company) → `Event Deep-Dive Agent` → `Historical Context Agent` → `Recommendation Synthesizer` → `Narrative Writer` → `evaluate_quality` → branch
- Output: "memo" artifact rather than a brief

### 7.6 Human-in-the-Loop Review Queue

When workflow confidence falls in the range 0.4–0.69 (D9), the output is routed to the HIL Review Queue rather than auto-dispatched.

**Queue UI (lives under `/admin/hil`):**
- Items sorted by scheduled send time
- Each item shows: report preview, confidence breakdown by node, key concerns, time-to-send countdown
- Actions: Approve / Edit & Approve / Reject / Reject with feedback

**Timing windows per workflow:**

| Workflow | Scheduled send | HIL review window | Unreviewed fallback |
|----------|---------------|-------------------|---------------------|
| Morning Brief | 06:00 | 22:00 prev – 05:45 | Hold; notify user to review |
| Watchlist Scan | 18:00 | 14:00 – 17:45 | Hold; notify user |
| Earnings Risk Brief | 18:00 | 14:00 – 17:45 | Hold; notify user |
| On-Demand Analysis | User-initiated | 10 min from generation | Deliver with low-confidence banner |
| Event Deep-Dive | Event-driven | 30 min from generation | Send with low-confidence banner |

Every HIL action writes to Layer 4 user feedback memory. Weekly, the offline job aggregates these signals and proposes adjustments.

### 7.7 Confidence Model and Routing Thresholds (D9)

```
Confidence ≥ 0.70  →  auto-send
Confidence 0.40–0.69  →  HIL review queue
Confidence < 0.40  →  blocked; not sent; episodic log entry only
```

Workflow confidence = minimum confidence across all critical AgentNodes.

Confidence is calibrated against ex-post outcomes (Tier 3 evaluation). If high-confidence recommendations do not outperform low-confidence ones in market outcomes, the confidence model is recalibrated.

## 8. Prompt Management

Prompts are version-controlled artifacts treated with the same discipline as code.

**Storage layout:**
```
prompts/
  agents/            relevance_analyst.md, anomaly_detector.md,
                     historical_context_agent.md, recommendation_synthesizer.md,
                     exposure_analyst.md, earnings_context_agent.md,
                     event_deep_dive_agent.md, narrative_writer.md, qa_analyst.md
  evaluators/        recommendation_judge.md, factuality_judge.md, calibration_judge.md
  classifiers/       event_classifier.md, tweet_classifier.md, ticker_extractor.md
```

**Hybrid model — git as source of truth, Langfuse as runtime access:**
- Git: version control, code review, disaster recovery, reproducibility, diff and merge tooling.
- Langfuse: edit-without-redeploying, trace linkage (every trace records the exact prompt SHA that produced it), A/B testing via labels (`production`, `staging`, `canary`, `experimental`).

**Promotion pipeline:**
1. Draft — modify `.md` file locally, iterate against small test set.
2. PR — pull request includes a Tier 2 golden dataset run report.
3. Review — focused on prompt clarity, anti-patterns, example validity.
4. Merge — CI publishes to Langfuse with git SHA as version, label `staging`.
5. Canary — promoted to label `canary` on a subset of production traffic.
6. Monitor — Tier 1 online judge and Tier 3 ex-post calibration on canary traffic.
7. Promote — after N days (configurable per agent), metrics holding → label `production`.

**Rollback:** Re-labeling the previous version as `production` in Langfuse takes effect within seconds. No deployment required.

**Prompt SHA** is used as the Langfuse version label. Every production trace links back to the exact prompt that produced it.

## 9. Evaluation Framework

Three evaluation tiers run from MVP. Observability tells you what happened; evaluation tells you whether it was correct.

**Tier 1 — Online LLM-as-Judge (every output)**
- Scope: every user-facing agent output (Recommendation Synthesizer, Narrative Writer, Event Deep-Dive Agent)
- Dimensions scored: factual grounding (are claims traceable to tool output?), confidence calibration, internal consistency, tool use appropriateness
- Judge model: Opus 4.7 (different model from the producing agent)
- Cost: $0.01–$0.03 per evaluation; runs asynchronously within ~5 seconds of output
- Results stored as Langfuse scores linked to the producing trace

**Tier 2 — Golden Dataset Regression (every prompt or model change)**
- A hand-curated set of ~50 historical events with expected analysis characteristics
- Stored in Langfuse Datasets; each example versioned and labeled by difficulty/category
- Gate: a prompt change cannot be promoted if it scores more than 5% worse than the current production version on any metric. Hard gate; no override without explicit acknowledgment.
- Dataset grows from HIL rejections, HIL edits, and user-flagged events

**Tier 3 — Ex-post Calibration (continuous, T+1d and T+1w)**
- For every `ai_recommendation`, `actual_t1d` and `actual_t1w` fields are filled from `price_bar` data the following day and week
- Calibration question: do high-confidence BULLISH recommendations outperform low-confidence ones in realized market outcomes?
- Key metric: `CORR(confidence, actual_t1d * direction_sign)` — should be significantly positive
- Dashboard: Langfuse dashboard updated daily; reviewed weekly minimum

**Continuous improvement loop:** Tier 3 surfaces systematic failures → investigation → Tier 2 regression on hypothesis fix → if improvement, deploy via promotion pipeline → Tier 1 confirms no regression on other dimensions → Tier 3 monitors real-world calibration improvement.

## 12. Cross-Cutting Concerns

### 12.1 Authentication and Authorization (D2)

- **Mechanism:** JWT access tokens (short-lived) + refresh tokens (long-lived). Access tokens sent in `Authorization: Bearer` header. Refresh tokens in HttpOnly cookies.
- **Credential storage:** Password hashed with bcrypt, cost factor ≥ 12.
- **Role model:** `admin` | `operator` | `end_user` — stored in `user.role` from day one. Role checked on every protected endpoint. Admin panel routes require `admin` role.
- **Endpoint policy:** Authentication required by default on all endpoints. Opt-out is explicit and code-reviewed.
- **Rate limiting:** Applied to all public mutation endpoints (login, token refresh, any write endpoint).
- **OAuth2:** Deferred to post-MVP. The user table schema is OAuth2-compatible.
- **IDOR prevention:** Resource ownership verified on every lookup (tenant_id + user_id check before returning any record).

### 12.2 Secrets Management (D3)

- **MVP:** All secrets in environment variables; loaded at startup; process fails fast if any required var is missing.
- **`.env.example`:** Committed to git. `.env` is in `.gitignore` and never committed.
- **`source_config.credentials_ref`:** Stores a reference string (e.g. `env:FINNHUB_API_KEY`), not the secret value. The `data_providers` module resolves references at runtime. Switching to HashiCorp Vault means changing the resolver, not the schema.
- **Never log:** Passwords, tokens, secrets, API keys, or PII must never appear in logs or stack traces returned to clients.

### 12.3 Multi-Tenancy

- Every user-owned table carries `tenant_id` from day one (D11 / Principle 3).
- All repository queries include `tenant_id` in the WHERE clause. No business-layer shortcut bypasses this.
- Multi-tenant activation (multiple live tenants) is deferred to Phase 5 — it requires configuration and activation of tenant isolation logic, not schema migration.
- `geo_event` uses `tenant_id = NULL` for global events (visible to all tenants) and a specific UUID for tenant-scoped events.

### 12.4 Observability

**Langfuse self-hosted** (PostgreSQL metadata + ClickHouse analytics backend) is the AI observability stack. It handles LLM-level tracing, prompt management, evaluation datasets, and scoring. It is not a replacement for standard APM.

Every workflow run produces one hierarchical Langfuse trace. Standard metadata on every span: `workflow_id`, `workflow_type`, `tenant_id`, `user_id`, `agent_role_id`, `prompt_version` (git SHA), `model_used`, `confidence`, `cost_usd`, `tokens_in`, `tokens_out`, `latency_ms`, `tools_called`, `state_snapshot_ref`.

**Standard application observability** (structured JSON logs, request_id propagation, error tracking) lives separately. Python logging at INFO level in production; DEBUG in development.

**Log policy:** Every request logged with method, path, status, duration, request_id. Every error logged with message, stack, request_id, user_id. No sensitive data in logs.

### 12.5 Portability and Self-Host Parity (D11 / Principle 4)

Self-hosting the entire system (replacing any managed cloud service) requires only environment variable changes and `docker compose up`. The docker-compose file covers: `api`, `worker` (Celery), `postgres` (TimescaleDB), `redis`, `langfuse-server`, `langfuse-db`, `clickhouse`.

No Azure-specific SDK calls anywhere in the codebase. Cloud-managed services map one-to-one to containerized alternatives:

| Azure service | Self-hosted equivalent |
|---------------|----------------------|
| Azure DB for PostgreSQL | `timescale/timescaledb-ha:pg16` container |
| Azure Cache for Redis | `redis:7` container |
| Azure Container Apps | Docker Compose / K8s |
| Azure Blob Storage | MinIO / local filesystem |
| Azure Key Vault | HashiCorp Vault / `.env` |
| Azure Monitor | Prometheus + Grafana |

**12-factor compliance:** All config from environment variables. Startup fails fast on missing required vars. Stateless application processes (state in PostgreSQL + Redis). Logs to stdout.

### 12.6 Cost Governance (D12)

Budget ceiling: AI + infrastructure < $100/month combined (D12).

**Three levels of budget enforcement:**

1. **Per-agent:** `cost_ceiling_usd` in agent YAML. Enforced at runtime; exceeded invocation fails and routes workflow to HIL.

2. **Per-workflow:** `cost_ceiling_usd` in workflow YAML. If ceiling is approached, subsequent agents receive reduced token budgets. If ceiling is hit, workflow stops and routes to HIL.

3. **Per-user/day:** `daily_budget_usd` in tenant config. Alert at `daily_alert_threshold_pct` (80% default). Hard stop at `daily_hard_stop_pct` (100%). Scheduled workflows queue for tomorrow when hard stop is reached.

**GDELT historical archive cold-start:** The event archive must be seeded from GDELT historical files (1979+) and paired with historical prices before the system goes live. Without this seed, the analogy engine cannot deliver meaningful results at launch ("8 similar historical events" requires the archive).

**Anti-fatigue controls** (per-user, stored in `user.settings`): `daily_push_limit` (default 5), `quiet_hours`, per-ticker intensity thresholds, deduplication window.
