# REQ-F-??? — Alert Dispatch with Anti-Fatigue Controls

## Domain Context
Steps 9–12 of the Mode A Reactive Pipeline. Sonnet 4.6 generates the alert text, per-user anti-fatigue rules are evaluated, and the alert is dispatched via SendGrid email or logged silent. Conditionally enqueues a Mode B deep-dive. Anti-fatigue prevents alert overload.

## Summary
The system must generate a ~80-word alert text using Sonnet 4.6 (≤8 s), evaluate per-user anti-fatigue rules (daily limit, quiet hours, per-ticker threshold, deduplication window), dispatch the alert via SendGrid when rules pass, or log it silent when suppressed; and enqueue a deep-dive Mode B job when intensity ≥ 4 or a portfolio match is detected.

## Detailed Description
As described in architectural-considerations-digest.md §Business Rules item 24 and root-synthesis §Alerting and Anti-Fatigue, per-user alert controls govern all dispatched notifications:
- daily_push_limit: maximum alerts per user per day
- quiet_hours: time window during which alerts are suppressed
- per_ticker_threshold: minimum re-alert interval per ticker
- deduplication_window: suppress alerts for the same event within the window

Per root-synthesis §Business Rules item 55, per-user/day cost limits (daily_budget_usd, daily_alert_threshold_pct, daily_hard_stop_pct) are also enforced before dispatch.

The alert text generated by Sonnet 4.6 must include: event headline, intensity indicator, number of holdings exposed, AI one-word action signal, confidence level, sample_size, and analogies citation. When sample_size < 5, a disclaimer is appended.

Every AI recommendation carries confidence level, historical sample size, and cited sources — displayed inline (root-synthesis §Business Rule 15).

Alert dispatch uses SendGrid (email channel). The alert_rule table drives which events trigger alerts for which users. Silent-logged alerts are retained in the DB for audit and are visible in the Alerts Center.

## Desired Outcome
Users receive timely, relevant alerts for high-impact events affecting their portfolio without being overwhelmed by notification fatigue, with full traceability of why each alert was sent or suppressed.

## Acceptance Criteria
- [ ] AC-001: Given a classified event where alert rules match a user, Sonnet 4.6 produces alert text of approximately 80 words within 8 seconds including confidence, sample_size, and action signal.
- [ ] AC-002: Given a user has reached their daily_push_limit, the alert is logged silent in the DB and no email is dispatched, without error.
- [ ] AC-003: Given an alert falls within the user's configured quiet_hours window, the alert is suppressed (logged silent) and is not dispatched until after quiet hours end, or is discarded per user preference.
- [ ] AC-004: Given an event with intensity ≥ 4 or a portfolio company match detected at step 12, a Mode B deep-dive Celery job is enqueued within the 90-second pipeline window.
- [ ] AC-005: Given sample_size < 5 in the analogy results, the alert text includes the low-sample disclaimer before dispatch.
- [ ] AC-006: Given a user's daily_hard_stop_pct is reached, no further alerts are dispatched for that user for the remainder of the day, regardless of event intensity.

## Process Sequence
1. Sonnet 4.6 generates ~80-word alert text with action signal and confidence (step 9)
2. System evaluates alert_rule table for matching users
3. For each matching user, anti-fatigue controls checked: daily limit, quiet hours, per-ticker threshold, deduplication window
4. Budget check: daily_budget_usd and hard_stop_pct evaluated
5. If all checks pass: alert dispatched via SendGrid, alert row status=dispatched
6. If any check fails: alert row status=suppressed_*, logged silent
7. Step 12: if intensity ≥ 4 or portfolio match → enqueue deep-dive job with 2-minute delay
